# Users Module — Profile Management

## Overview
This PR adds three new features to the `users` module:
1. Edit profile information
2. Update profile picture
3. Update email address (with verification, local accounts only)

All changes are isolated to the `users` module and follow the existing patterns in the codebase.

---

## New Endpoints

| Method | Route | Auth | Description |
|--------|-------|------|-------------|
| `PATCH` | `/me/profile` | JWT | Edit first and/or last name |
| `PATCH` | `/me/profile-photo` | JWT | Update profile photo URL |
| `PATCH` | `/me/email` | JWT | Request an email change |
| `GET` | `/me/confirm-email-change?token=` | None | Confirm new email from link |

## Files Changed

### `src/users/users.controller.ts`
- Added `PATCH /me/profile` — calls `editProfile()`
- Added `PATCH /me/profile-photo` — calls `updateProfilePhoto()`
- Added `PATCH /me/email` — calls `requestEmailUpdate()`
- Added `GET /me/confirm-email-change` — calls `confirmEmailChange()`
- Used `@Patch` instead of `@Put` for partial updates since none of these replace the full resource
- `confirm-email-change` has no `@UseGuards` intentionally — the user clicks this from their email inbox so there is no JWT available. The JWT inside the token itself acts as authentication

### `src/users/users.service.ts`
- Added `editProfile()` — updates `firstName` and/or `lastName`, only updates fields that are provided
- Added `updateProfilePhoto()` — updates `profilePhotoURL` with a URL string. Cloudinary integration will be added later; for now only the URL is stored as agreed
- Added `requestEmailUpdate()` — verifies the user's current password first before sending a verification email to the new address. This prevents someone who grabbed a logged-in session from silently changing the email
- Added `confirmEmailChange()` — verifies the token from the email link, checks the purpose is `email-change`, then updates the email in the database
- Injected `EmailVerificationLib` since it was already built and had `sendEmailChangeVerification()` ready to use

### `src/users/users.module.ts`
- Added `EmailVerificationLib` to `providers`
- Added `JwtModule` to `imports` because `EmailVerificationLib` depends on `JwtService` to sign and verify tokens

### `src/users/dto/edit-profile.dto.ts` *(new file)*
- `firstName` and `lastName` are both `@IsOptional()` so the user can update just one or both

### `src/users/dto/update-profile-photo.dto.ts` *(new file)*
- `profilePhotoURL` validated with `@IsUrl()` to ensure only valid URLs are stored

### `src/users/dto/update-email.dto.ts` *(new file)*
- `newEmail` validated with `@IsEmail()`
- `password` required to confirm the user's identity before the change is processed

## Decisions Made

### Why `@Patch` and not `@Put`?
`PUT` replaces the entire resource. `PATCH` updates part of it. Since we're only updating one or two fields at a time, `PATCH` is the correct HTTP verb.

### Why require the current password before changing email?
If someone steals a logged-in session (e.g. leaves a laptop open), they could silently change the email and lock the real user out. Requiring the current password adds a second layer of protection against account takeover.

### Why send the verification to the NEW email and not the current one?
The goal is to prove ownership of the new address before switching to it. Sending to the current email would only prove the user already has access to it, which we already know since they're logged in.

### Why is `confirm-email-change` not protected by JWT?
The user clicks the link from their email client, where there is no session or JWT. The signed token in the query string (generated by `EmailVerificationLib`) is what authenticates the request — it contains the `userId`, `newEmail`, and `purpose`, and expires in 1 hour.

### Why only allow email changes for `authProvider === LOCAL`?
Google accounts use Google as the source of truth for the email address. Changing the email on a Google account locally would break the login flow since Google would still return the old email on sign-in.

### Why store only the URL for profile photos?
Cloudinary integration is not set up yet. The endpoint is built now so the frontend can integrate immediately. Once Cloudinary is ready, a separate upload endpoint will be added that returns a URL, and the frontend will pass that URL to this endpoint — no breaking changes needed.
